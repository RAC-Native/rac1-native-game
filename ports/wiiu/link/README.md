# rac1-link (prototype)

The first step of the Wii U launcher + PC backend design (`LAUNCHER_DESIGN.md`, section 7.1 "xfer-test", made
reusable): a small Wii U homebrew that receives files from the PC over the LAN, and the PC tool that sends them and
measures the link. It does not start the game yet, and it carries no game code or data.

| Folder | What |
|---|---|
| `core/` | The receiver: protocol, pipeline, manifest, path whitelist, hashes. Portable C11 + POSIX + pthreads. The **same code** runs on the console and in the PC stand-in. |
| `console/` | The Wii U app (`rac1-link.rpx` / `.wuhb`): WHB console text on TV + GamePad, ProcUI, network wait, somemopt option. |
| `host/` | `rac1-link-host`: the receiver built for a PC (a folder stands in for the SD card), for the loopback test. |
| `pc/rac1_link.py` | The PC side, Python 3 standard library only: discover, pair, status, send, bench, config, quit. |
| `pc/test_loopback.py` | The loopback test (generated data only). |

## Build

Everything builds outside the source tree; nothing of the game is needed (no PC build, no setup).

```sh
# the console app (devkitPPC + wut): rac1-link.rpx, and rac1-link.wuhb when wut-tools' wuhbtool is installed
/opt/devkitpro/portlibs/wiiu/bin/powerpc-eabi-cmake -S ports/wiiu/link/console -B ~/progetti/rac1-scratch/rac1-link/build-wiiu
cmake --build ~/progetti/rac1-scratch/rac1-link/build-wiiu -j 3
/opt/devkitpro/tools/bin/readrpl -i ~/progetti/rac1-scratch/rac1-link/build-wiiu/rac1-link.rpx   # imports

# the PC stand-in and the loopback test (~450 MB of temporary files in --work, deleted at the end)
cmake -S ports/wiiu/link/host -B ~/progetti/rac1-scratch/rac1-link/build-host && cmake --build ~/progetti/rac1-scratch/rac1-link/build-host -j 3
python3 ports/wiiu/link/pc/test_loopback.py --host-bin ~/progetti/rac1-scratch/rac1-link/build-host/rac1-link-host \
    --work ~/progetti/rac1-scratch/rac1-link/loopback
```

The `.rpx` imports only system libraries: coreinit, nsysnet, nn_ac, nn_nets2 (somemopt), proc_ui, sysapp, vpad.

## Run on the console

Start it with Aroma's wiiload plugin; its screen and its UDP log (port 4405) show the IP and the **pairing code**.

```sh
L=~/progetti/rac1-scratch/rac1-link
# 1. send and start it, and keep its UDP log (wiiu-run.sh checks FTP port 21 first; see below without FTPiiU)
WIIU_IP=192.168.0.16 WIIU_TIMEOUT=3600 ports/wiiu/tools/wiiu-run.sh $L/build-wiiu/rac1-link.rpx &
#    without FTPiiU:   socat -u UDP-RECV:4405,reuseaddr - | tee $L/console.log &
#                      WIILOAD=tcp:192.168.0.16 /opt/devkitpro/tools/bin/wiiload $L/build-wiiu/rac1-link.rpx

# 2. find it and pair (the code is on the TV, and in the UDP log as "Pairing code: NNNNNN")
python3 ports/wiiu/link/pc/rac1_link.py discover
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 pair --code NNNNNN

# 3. measure: small first, then the real numbers (one --mb per mode; 64 MiB at 1 MiB/s is about a minute)
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 bench --mode all --mb 64
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 bench --mode all --mb 1024
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 bench --mode sd --mb 256 --files 1000 --chunk-kib 256
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 bench --mode sd --mb 256 --fwrite

# 4. socket options (apply from the next connection), then measure the network again
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 config --rcvbuf 262144 --winscale 1 --sack 1
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 bench --mode net --mb 256
#    somemopt applies from the next start of rac1-link: config --somemopt 1, then quit and start it again

# 5. a real file with resume (interrupt it with Ctrl-C or HOME, run it again), then the state on the card
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 send some-big-file.bin --dest rac1-native/test/big.bin
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 status

# 6. back to the Wii U Menu (wiiu-run.sh then prints the log and exits)
python3 ports/wiiu/link/pc/rac1_link.py --console 192.168.0.16 quit
```

Without `--console` the PC broadcasts and takes the only console that answers (then the last one used). The pairing
code is saved per console in `~/.config/rac1-link/consoles.json` (`RAC1_LINK_CONFIG` overrides the path), and on the
card in `sd:/rac1-native/.link/pair.txt` (delete it for a new code). `--json` prints JSON lines for a GUI.

## What each mode measures

| Mode | Console does | Measures |
|---|---|---|
| `bench --mode net` | receives and drops (no CRC, no SHA-1, no card) | **the network alone** |
| `bench --mode net-hash` | receives, CRC-32 + SHA-1, drops | the network plus the console's hashing (CPU) |
| `bench --mode sd` | writes N MiB of generated bytes from memory, fsync, renames, reads back, deletes | **the SD card alone**: write, rename, read, delete; `--files`, `--chunk-kib`, `--fwrite` (unaligned stdio) vary it |
| `bench --mode both` | the full path: receive, CRC, SHA-1, write `.part` (pipelined), fsync, verify, delete | **network + SD together** |
| `send` | the full path, renamed into place and recorded in the manifest | real transfers, with resume |

For every transfer the PC prints its own wall rate and the console's: `wall` (BEGIN to END on the console), `net`
(waiting for and receiving data), `sd` (the writer thread's write + fsync time), `hash` (CRC + SHA-1), and how long the
receive thread waited for a free buffer (the card is the bottleneck when that is large). Rates are MiB/s. The console
prints one line per file of 1 MiB or more, a progress line every 2 s, and the same lines go to UDP 4405.

## The protocol (v1, as built)

`core/link_proto.h` has the numbers. One TCP connection (PC to console, port 47199); a 12-byte header
`'R' '1' type flags length seq`; control messages are `key=value` lines; `DATA` is `offset:u64 crc32:u32` + at most
1 MiB. Discovery: `RAC1LINK?` to UDP 47198, answered by unicast `RAC1LINK! proto=… name=… port=… serial=…`.

- **Pairing.** The console sends a nonce in `HELLO`; the PC answers HMAC-SHA256(key, "pc"+nonces), the console
  answers HMAC-SHA256(key, "console"+nonces), key = SHA-256("rac1-link pairing v1:" + code). Nothing but `PING`/`BYE`
  works before that. Wrong codes cost 1 s each, 5 in a row lock pairing for a minute.
- **Files.** `BEGIN_FILE path size sha1` → `READY offset` (non-zero: resume) → `DATA`… → `END_FILE` →
  `FILE_OK` (with timings) or `FILE_BAD`. The console writes `path.part` from 64-byte-aligned 1 MiB buffers on a writer
  thread (a ring of 6), fsyncs and sends `ACK offset` every 16 MiB, checks the SHA-1, renames (an existing file goes
  to `.old` first, then is removed). A chunk with a bad CRC gets `RESEND offset`; three bad chunks fail the file and
  delete the `.part`.
- **Manifest** `sd:/rac1-native/.link/manifest.txt`: `F` (committed: size, SHA-1, path) and `P` (a `.part` of 8 MiB or
  more in progress). `send` skips files the console has with the same size and SHA-1; a file counts as installed only
  if it is also on the card with that size. Resume restarts from the `.part`'s size rounded down to 1 MiB; the console
  re-reads that prefix to rebuild the SHA-1 (its time is reported as `rehash_ms`).
- **Whitelist.** Only relative paths under `rac1-native/` (not `rac1-native/.link/`) or `wiiu/apps/rac1-native/`; no
  `..`, `.`, empty components, backslashes, drive letters, FAT-invalid or control characters, trailing dots or
  spaces, `.part`/`.old` names, over 240 bytes. Files over 4 GiB - 1 are refused. Peers outside loopback, RFC 1918 and
  link-local addresses are refused (TCP and discovery).
- **HOME.** On ProcUI release the session is closed (the `.part` is kept), the listener closed and discovery silent;
  on return it listens again and the PC resumes with the same `send`.

## The loopback test

`pc/test_loopback.py` runs `rac1-link-host` on a temporary folder and drives `rac1_link.py` against it: self-test
(hash known answers, 35 whitelist cases, peer filter), discovery, pairing (unpaired, wrong code, right code, raw
commands before AUTH), a 200 MiB random file (SHA-1 on disk, no `.part` left, manifest, skip when unchanged), resume
after a dropped connection, after `kill -9` of the PC and after `kill -9` of the receiver, HOME (SIGUSR1 on the
stand-in), CRC failures (two resent chunks; every chunk bad → `FILE_BAD`, `.part` deleted), ten bad paths refused
with nothing written outside, a 30-file folder and its update (1 sent, 29 skipped, no `.old` left), the bench modes,
`config` (new listener) and `quit`.

## Known limits (prototype)

- **Not run on a console yet.** Unknowns for the first test: FSA's behaviour on `ftruncate` and re-opening a `.part`
  on resume, `statvfs` on `fs:/vol/external01`, whether pthreads from wut land on a sensible core (`affinity=1` in
  `link.cfg` pins net to core 2, writer to core 0), and somemopt (3 MiB, `socket_lib_finish` at exit to end it).
- The pairing code also goes to the UDP log (handy for remote tests; to remove for v1), and it is kept on the card,
  not a per-PC key derived with PBKDF2 as the design says. Any PC with the code can pair; there is no "pairing screen".
  A 6-digit code is brute-forceable offline from one captured handshake. No encryption.
- The console's random numbers are the time base hashed with SHA-256, not a CSPRNG.
- No `COMMIT`/generation, no `commit.log`, no `.wuhb` swap, no launching of the game, no self-update, no free-space
  check across a whole folder (per file only), no `PROGRESS` from a PC setup (only the file name).
- Small files are written and fsync'd one by one (no batching); the manifest is a linear list (thousands of files
  are fine, not tens of thousands), saved after big files and every 5 s.
- Discovery sends only to 255.255.255.255 (or `--broadcast ADDR`, repeatable), not to each interface's directed
  broadcast.
- The UI is the scrolling WHB log: no progress bar, no menu; A shows the IP and code again.
